# 001. 백엔드 스택과 MVP 범위

- 상태: Accepted
- 날짜: 2026-10-12

## Context (배경)

- 12주(9/22~12/14) 2인 캡스톤 프로젝트이며 백엔드·데이터·AI를 1인이 담당한다.
- 프로젝트 계획서(FastAPI, PostgreSQL, GPT-4o-mini)와 기획 발표자료(RAG·Vector DB 언급)가 LLM으로 순차 생성되어 표현이 일부 다르다.
- 공공 API(온통청년, 금감원)는 호출 제한과 지연 위험이 있다.
- 백엔드 개발 착수 시점(3주차 말)에 저장소가 비어 있어 골격부터 세워야 했다.

## Decision (결정)

- **FastAPI(async) + PostgreSQL + SQLAlchemy 2(asyncpg)**, 패키지 관리는 **uv**.
- 공공 데이터는 **일 1회 배치로 PostgreSQL에 미러링**하고 요청 경로에서는 외부 API를 호출하지 않는다.
- 후보 축소는 SQL/메타데이터로 처리하고, LLM은 역질문 생성과 근거 서술에만 사용한다.
- **MVP에서는 별도 Vector DB를 도입하지 않는다.** RAG는 "SQL로 필터된 후보 레코드의 메타데이터만 LLM 컨텍스트로 제공"하는 형태로 정의한다. 자연어 유사도 검색이 필요해지면 `pgvector`로 PostgreSQL을 확장한다.
- MVP 데이터는 서울·경기 핵심 정책 50~100건 + 금감원 공시 적금으로 한정한다.

## Alternatives (검토한 대안)

| 대안 | 장점 | 단점 | 채택하지 않은 이유 |
|------|------|------|--------------------|
| Django / Spring Boot | 관리자·ORM 내장 / 안정적 | 비동기 LLM 호출·Python AI 생태계와 거리, 설정 비용 | 계획서와 일정상 FastAPI가 적합 |
| 처음부터 Chroma 등 Vector DB | 의미 검색 즉시 가능 | 인프라 증가, 정규화된 자격 조건 매칭에는 불필요 | 자격 매칭은 구조화 필드로 충분, 필요 시 pgvector |
| 요청 시 외부 API 실시간 호출 | 구현 단순, 항상 최신 | 호출 제한·지연·장애 전파 | 배치 미러링으로 가용성 확보 |

## Consequences (결과)

- 응답 지연과 외부 장애 영향이 줄고, LLM 컨텍스트가 작아져 비용이 통제된다.
- 정책 원문 → 구조화 필드 정규화 품질이 추천 정확도를 좌우한다 (2차 Build 핵심 과제).
- 발표자료의 "Vector DB" 표기와 구현이 다르므로 발표 시 "pgvector 확장 가능" 으로 설명한다.

## 이력서·면접용 한 줄

"공공 API 호출 제한·환각 위험을 고려해 일 배치 미러링 + SQL 1차 필터 + 제약 기반 LLM 생성 구조로 설계, 불필요한 Vector DB 도입 없이 PostgreSQL 중심 아키텍처로 MVP 범위를 통제함."
