# 003. 일 배치 미러링: 미수집 행 삭제에 완전 수집 + 5% 상한 조건

- 상태: Superseded by 010 (금감원 권역별 삭제 판단과 금리 옵션 교체 규칙만. 정책 삭제 안전장치는 유효)
- 날짜: 2026-10-18

## Context (배경)

- 온통청년·금감원 데이터는 일 1회 배치로 DB에 미러링하고, 추천은 DB 값만 쓴다. 원본에서 사라진 정책·상품을 지우지 않으면 끝난 정책이 계속 추천된다.
- 반대로 API가 일시 장애로 적은 건수를 돌려줄 때 그대로 지우면 미러가 비고, 다음 배치까지 추천이 멈춘다.
- 실제로 온통청년은 재적재 중 HTTP 500이 2회 발생했다 (재시도로 회복). 응답 이상은 드물지 않다고 보고 설계해야 한다.
- 첫 구현은 "API가 알려준 전체 건수만큼 받았으면 나머지 삭제"였다. 리뷰에서 두 가지 구멍이 나왔다.
  - API가 전체 건수 10건과 정책 10건을 돌려주면 완전 수집으로 판정되어 기존 3,250여 건이 삭제된다.
  - 받은 건수에 중복이 섞이면 누락이 있어도 완전 수집으로 판정된다.

## Decision (결정)

미수집 행은 아래 두 조건을 **모두** 만족할 때만 삭제한다. 하나라도 어긋나면 한 건도 지우지 않고 `partial`로 기록한다.

1. **완전 수집**: API가 알려준 전체 건수 이상을 **중복 없이** 받았다.
2. **삭제 상한**: 삭제 대상이 **적재 전** 기존 행의 **5% 이하**다 (`MAX_PRUNE_RATIO = 0.05`). 정책 3,262건 기준 163건.

- 상한 비교 기준은 upsert 전 행 수다. upsert 후 행 수를 쓰면 새로 들어온 행만큼 상한이 커진다.
- 금감원은 권역(은행·저축은행)별로 판단하고, 금리 옵션은 이번에 받은 상품의 것만 교체한다.
- 상한을 넘으면 보고서에 "삭제 대상 N건이 상한을 넘어 건너뜀 (원본 확인 필요)"를 남기고, 사람이 원본을 확인한 뒤 처리한다.

## Alternatives (검토한 대안)

| 대안 | 장점 | 단점 | 채택하지 않은 이유 |
|------|------|------|--------------------|
| 삭제하지 않음 (upsert만) | 데이터 손실 위험 없음 | 끝난 정책이 영구히 남아 추천됨 | 추천 정확도(DB 값만 신뢰) 원칙과 충돌 |
| 완전 수집 조건만 | 구현 단순 | API가 적은 전체 건수를 함께 주면 대량 삭제 | 리뷰에서 재현 가능한 구멍 확인 |
| soft delete (`is_active` 플래그) | 복구 쉬움 | 모든 조회에 조건 추가, 스키마 변경 | 상한으로 대량 삭제 자체를 막는 편이 단순. 필요해지면 재검토 |
| 상한 10~20% | 대규모 정리도 자동 처리 | 장애 시 손실 폭이 큼 | "DB가 비는 일은 없어야 한다"는 요구에 맞춰 보수적으로 5% |

## Consequences (결과)

- API가 1건만 돌려줘도 기존 미러는 보존된다 (DB 통합 테스트로 검증).
- 하루에 5%를 넘는 정당한 정리(대규모 사업 종료 등)는 자동으로 처리되지 않는다. 보고서의 `partial`과 note를 보고 수동 처리해야 한다.
- 정책 일일 변동이 5%를 자주 넘는지는 운영 후 `ingest_runs`의 `partial` 빈도로 확인하고, 필요하면 상한을 조정한다 (측정 전).
- 관련 코드: `app/ingest/loader.py`(`prune_allowed`, `_prune_stale`), `app/ingest/pipeline.py`(`is_complete_fetch`).

## 이력서·면접용 한 줄

"공공 API 일 배치 미러링에서 완전 수집 확인 + 삭제 5% 상한을 두어, API 일시 장애 시에도 서비스 데이터가 대량 삭제되지 않도록 설계함"
