# 008. 역질문 변수 선정: 기대 제거율 + 템플릿 질문 + PostgreSQL 세션

- 상태: Accepted
- 날짜: 2026-11-03

## Context (배경)

- 1차 룰 필터(ADR 006) 뒤 서울·경기 사용자 후보는 360건 이상이다. 역질문 3~5개로 "자격이 확실히 없는 정책"을 지워야 한다.
- 계획은 LLM이 후보를 보고 역질문 JSON을 만드는 방식이었다. 하지만 어떤 변수를 묻느냐는 후보 수만 세면 정해지는 계산이고, LLM이 고른 변수·선택지는 필터 코드와 어긋날 수 있다(환각 방지 원칙).
- 질문 후보 변수 6개(혼인·학력·특화·전공·소득·시군구)의 분포를 재 보니, 코드표의 "기타"는 서로 다른 조건을 묶은 값이고 특화 코드는 "해당자만"과 "우대"가 섞여 있었다. 소득 금액은 단위가 섞여 있다(`journal/2026-11-02-question-engine.md`).
- 정렬이 일부 시군구 정책을 뒤로 밀어서(ADR 006) 상위 50만 보면 경기 사용자의 일부 시군 정책 38건이 모두 빠진다.
- 질문과 답을 여러 요청에 걸쳐 이어야 하므로 세션 상태를 둘 곳이 필요하다. 알파 테스트(10주차)에서 질문 전후 후보를 분석할 데이터도 남겨야 한다.

## Decision (결정)

- **변수 선정은 서버가 한다.** 아직 모르는 변수마다 선택지별로 빠지는 후보 수를 세고, 선택지가 고르게 답해진다고 가정한 **기대 제거율**(빠지는 후보 비율의 평균)로 점수를 매긴다. 빠질 수 있는 후보 3건 이상, 점수 0.01 이상인 변수만 점수 순으로 최대 5개 묻는다. 기준을 넘는 변수가 3개 미만이면 있는 만큼만 묻는다.
- **점수는 전체 후보로 계산한다.** 상위 50이 아니라 limit 없이 조회한 전체 후보(최대 약 370건)를 쓴다.
- **질문 변수는 4개**: 혼인, 학력, 본인 연소득 구간, 시군구. 모두 단일 선택이다. 특화·전공은 제외한다.
- **필터 의미는 "확실히 맞지 않는 정책만 지운다".** 코드 없음·제한없음·기타·비기타 전부 나열은 통과, 소득은 `earn_max`가 1,000~20,000(만원)일 때만 쓴다. 시군구는 `region_scope=sigungu` 정책만 거르고, 사용자 시군구를 포함하는 정책은 시도 전체와 같은 순위로 올린다.
- **질문 문구는 우선 템플릿**으로 만든다. 3차 LLM은 서버가 고른 변수·선택지의 문구만 다듬고, 변수와 선택지 `value`는 바꾸지 않는다.
- **파이썬 판정과 SQL 필터를 테스트로 묶는다.** 질문 점수는 파이썬 판정 함수로, 답 반영은 SQL로 하므로 두 결과가 같은지 조합 테스트로 고정한다.
- **세션은 PostgreSQL `sessions` 테이블**에 저장한다. 1차 조건·질문·답(JSONB), 기준일 `as_of`, 답 전후 정책 ID를 남기고 생성 후 24시간 뒤 만료한다. 답은 저장된 질문의 선택지와 대조하고, 재조회 기준일은 `as_of`로 고정한다. 다시 답하면 1차 조건에 처음부터 다시 반영해 덮어쓴다.
- **적금 역질문은 하지 않는다.** 가입 대상·우대조건이 자유 텍스트라 거를 정형 변수가 없다.

## Alternatives (검토한 대안)

| 대안 | 장점 | 단점 | 채택하지 않은 이유 |
|------|------|------|--------------------|
| LLM이 후보를 보고 변수·질문을 생성 | 구현이 간단, 문구가 자연스러움 | 변수·선택지가 필터 코드와 어긋날 수 있음, 후보 370건을 넣으면 토큰 비용, 결과 재현 불가 | 변수 선정은 계산 문제. 문구만 LLM에 맡김 |
| 엔트로피 기반 정보 이득 | 이론적으로 표준 | 후보가 "남는다/빠진다" 두 상태뿐이라 이득이 제거율과 거의 같은 순서, 설명이 어려움 | `affected`와 함께 근거로 보여 주기 쉬운 제거율 선택 |
| 상위 50만으로 점수 계산 | 응답이 빠름, 화면 후보와 일치 | 정렬이 뒤로 미는 일부 시군 정책을 영원히 묻지 않음(경기 사용자 38건) | 세션 생성이 약 35ms 늘어도 전체 후보로 계산 |
| 특화·전공도 질문 | 변수 수 증가 | 특화는 해당자만·우대 혼재, 기타 42%. 전공은 상위 50 제한 4건 이하 중 3건이 학력과 중복 | 잘못 지울 정책이 생기거나 변별력이 없음 |
| Redis 세션 | TTL 내장, 빠름 | 인프라 추가(무료 개발 서버에 없음), 알파 테스트 분석 데이터가 휘발 | 쓰기 1~2회/세션이라 PostgreSQL로 충분 |
| 무상태(조건을 클라이언트가 들고 다님) | 저장소 불필요 | 질문·선택지를 서버가 검증할 수 없음, 분석 데이터 없음 | 선택지 대조와 분석 요구 불충족 |

## Consequences (결과)

- 대표 사용자 4명 모두 질문 3~4개가 나왔고, 전부 답하면 후보가 A 362 → 306, B 368 → 295, C 48 → 44, D 46 → 39건으로 줄었다. B는 평택시로 답하면 상위 50에 평택 정책 14건이 들어온다(답 전 0건).
- 세션 생성·답변·조회 모두 로컬 100ms 미만(5회 중앙값 31~90ms). 세션 생성은 전체 후보 조회와 INSERT 때문에 후보 API보다 최대 약 35ms 느리다.
- LLM 없이 질문·답·재필터가 끝까지 동작하므로, LLM 장애 때도 템플릿 질문으로 서비스할 수 있다.
- 감수하는 것:
  - 소득 질문은 낮은 구간으로 답하면 지우는 정책이 없다. 소득 기타(자유 텍스트 442건)·특화·전공 조건은 거르지 못하므로 선정 사유 단계에서 "확인 필요"로 보여 줘야 한다.
  - 선택지 균등 가정은 실제 사용자 분포(예: 대졸이 많음)와 다르다. 알파 테스트 답 분포로 가중치를 다시 볼 수 있다.
  - 시군구 이름표가 없는 시도 12(전남광주통합)·28(인천)·36(세종)은 시군구를 묻지 않는다.
  - 만료된 세션 행은 지우지 않고 남는다. 정리 작업은 알파 테스트 전에 정한다.
- 후속: LLM 질문 문구화(서버 변수·선택지 고정), LLM 선정 사유, 통합 패키지(7주차).

## 이력서·면접용 한 줄

"LLM에 맡기려던 역질문 변수 선정을 기대 제거율 계산으로 바꾸고 전체 후보 기준으로 점수를 매겨, 정렬에 가려 묻지 못하던 시군구 질문을 살리고 질문 3~4개로 후보를 최대 약 20%(368 → 295건) 줄임"
