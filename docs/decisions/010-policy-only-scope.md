# 010. 추천 범위를 청년 정책으로 한정 (적금 제외)

- 상태: Accepted
- 날짜: 2026-11-13

## Context (배경)

- ADR 001은 MVP 데이터를 "서울·경기 핵심 정책 + 금감원 공시 적금"으로 정했고, 2차 Build에서 금감원 적금 337건(금리 옵션 1,534건)을 일 배치로 적재했다.
- 적금 중 청년 상품은 8건(2.4%, 은행 4·저축은행 4)뿐이다(`journal/2026-10-26-data-quality-report.md`).
- 가입 대상·우대 조건이 자유 텍스트라 거를 정형 변수가 없다. 그래서 ADR 008에서 적금 역질문을 뺐다. 후보 API는 사용자 조건과 상관없이 "청년 상품 우선 → 최고 우대금리 순" 20건을 돌려줬고, 대표 사용자 4명 모두 같은 청년 상품 8건이 맨 앞에 왔다(`journal/2026-10-26-candidates-filter.md`). 개인화가 되지 않는다.
- 적금 API에는 상품 URL이 없어 공식 링크가 금융회사 홈페이지였다(ADR 005). 자격 근거로 보여 줄 페이지가 아니다.
- 정책은 전체 3,602건(서울·경기 960건)이고 나이·지역·취업상태·혼인·학력·소득 같은 정형 자격 필드가 있어 심화할 여지가 크다.
- 멘토 상담(2026-11)에서 정책·금융상품 중 하나에 집중해 깊이를 만들라는 조언을 받았다. 남은 일정(8~12주차)은 백엔드·데이터·AI를 1인이 맡는 상황에서 둘 다 심화하기에 부족하다.

## Decision (결정)

- 추천 대상을 **온통청년 정책으로 한정**한다. 금감원 적금의 적재 코드(`app/ingest/fss.py` 등), 모델, 테이블(`financial_companies`, `saving_products`, `saving_product_options`), API 응답의 `savings` 필드를 모두 제거한다.
- 테이블은 Alembic 리비전 `d4a8c2f6b1e9`로 삭제한다. downgrade는 초기 스키마 정의로 빈 테이블을 다시 만든다.
- 이 ADR은 ADR 001의 MVP 데이터 범위 중 **적금 부분만** 대체한다. 스택, 일 배치 미러링, SQL 1차 필터, Vector DB 미도입 결정은 그대로 유효하다. ADR 002의 적금 테이블 규칙, ADR 003의 금감원 권역별 삭제 규칙, ADR 005의 적금 링크 규칙, ADR 006의 적금 정렬 규칙도 더 이상 적용되지 않는다(각 ADR 상태에 부분 Superseded 표시).
- 배포는 코드 제거와 테이블 삭제를 한 번에 한다. Render는 새 컨테이너가 `alembic upgrade head`를 실행한 뒤 헬스체크를 통과할 때까지 이전 인스턴스로 요청을 받으므로, 그 사이 `/v1/candidates`·`/v1/sessions` 요청은 삭제된 테이블을 조회해 500이 날 수 있다. 개발 서버이고 알파 테스트(11/24) 전이라 이 짧은 구간을 감수한다. 04:00 KST 일 배치 시간은 피한다.
- 관심분야 `finance`는 유지한다. 정책 대분류의 금융 지원 정책(예: "취약계층 및 금융지원")을 고르는 필터라 적금과 무관하다.
- 7주차 "통합 패키지(지원금+적금)" 일정은 정책 심화(최종 후보 LLM 선정 사유, 이후 서류 준비 지원)에 쓴다.

## Alternatives (검토한 대안)

| 대안 | 장점 | 단점 | 채택하지 않은 이유 |
|------|------|------|--------------------|
| 적금 유지 (현행) | 기획서의 "정책 + 금융 통합 패키지" 차별점 유지 | 모든 사용자에게 같은 20건, 청년 상품 8건, 링크가 회사 홈페이지 | 추천이라 부를 개인화가 없음 |
| 적재는 두고 API 응답에서만 숨김 | 되살리기 쉬움 | 배치·테이블·API 키·테스트 유지비가 계속 듦 | 되살릴 계획이 없고, 필요하면 git 이력과 downgrade로 복구 가능 |
| 청년 상품 8건만 남김 | 청년 서비스 취지에 맞음 | 조건이 자유 텍스트라 여전히 사용자와 매칭 불가 | 8건 고정 목록은 정적 안내로 충분 |
| 적금에 집중하고 정책 축소 | 상품 구조가 단순 | 337건·정형 조건 없음, 서비스 핵심 가치(자격 근거)와 거리 | 데이터 규모·정형성이 정책 쪽이 압도적 |

## Consequences (결과)

- 얻는 것
  - 코드·테스트 약 1,070줄 삭제(모델 3개, 적재 클라이언트·로더·정규화·리포트 집계, 적금 테스트).
  - 일 배치에서 금감원 호출과 적금 337건·옵션 1,534건 적재가 빠진다. 2026-10-26 적재 기준 API 호출 43회 중 금감원 몫은 약 6회(추정).
  - 남은 일정을 정책 자격 근거·선정 사유 품질에 쓴다.
- 감수하는 것
  - 기획서·발표자료의 "통합 패키지" 차별점이 사라진다. 발표 메시지를 "정책 자격 근거 중심"으로 고쳐야 한다(팀장과 협의).
  - 프론트는 `savings` 필드와 `url_source: company_homepage` 처리를 지워야 한다.
  - 운영 DB의 적금 데이터는 마이그레이션과 함께 지워진다. downgrade는 빈 테이블만 만들며, 데이터는 배포 전 `pg_dump` 백업에서 복원하거나 클라이언트 코드 복원 후 재적재해야 한다.
  - 롤백은 DB를 먼저 되돌려야 한다. 이 리비전 파일이 있는 코드에서 `alembic downgrade b7e3f1a2c5d8`을 실행한 뒤 이전 코드를 배포한다. 코드부터 되돌리면 DB에 기록된 `d4a8c2f6b1e9`를 찾지 못해 컨테이너가 기동하지 못한다.
- 후속: 머지 전 프론트 담당 확인(`savings`·`company_homepage`를 읽는 코드가 있으면 프론트를 먼저 배포), 배포 직전 적금 테이블 3개 `pg_dump`, 배포 후 하루 문제가 없으면 GitHub Secrets의 `FSS_API_KEY` 삭제. `docs/reference/`의 계획서·발표자료 정리본은 원문이라 수정하지 않는다.

## 이력서·면접용 한 줄

"적재 데이터 분석(청년 적금 8/337, 자격 조건 자유 텍스트)으로 개인화가 불가능한 적금 추천을 근거와 함께 걷어내고, 남은 일정을 정형 자격 필드가 있는 정책 추천 심화에 집중함"
