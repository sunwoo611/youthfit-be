# 2026-11-13 LLM 선정 사유 구현과 측정 준비

## 상황 / 증상

최종 후보 상위 5건에 LLM 선정 사유를 붙이는 `POST /v1/sessions/{id}/recommendations`를 만들었다(결정: `decisions/011`). 단계마다 리뷰하면서 "LLM이 실패하면 빠르게 템플릿으로 대체한다", "확인하지 않은 자격을 맞다고 쓰지 않는다"는 의도를 깨는 결함이 여럿 나왔다. 실측을 준비하다가 토큰 로그가 서버에서 출력되지 않는 문제도 발견했다.

## 원인 분석

### LLM 클라이언트

1. **`LLM_TIMEOUT_SEC`(15초)가 전체 한도가 아니었다.** OpenAI SDK의 타임아웃은 시도 1회에만 걸린다. 재시도 1회가 붙고, 재시도 전에 서버의 `retry-after`를 최대 120초까지 기다린다(SDK `MAX_RETRY_AFTER_DELAY`). 최악이면 요청 하나가 약 150초 묶인다. 테스트가 모두 `max_retries=0`이라 드러나지 않았다.
2. **`LlmError`로 감싸지 않는 예외가 있었다.** SDK는 200 응답 형식을 검증하지 않는다(`_strict_response_validation=False`). 프록시가 HTML이나 깨진 JSON을 200으로 주면 `AttributeError`·`JSONDecodeError`가, `choices`가 비면 `IndexError`가 그대로 나가 템플릿 대체 대신 500이 된다.

### 캐시

3. **캐시를 비우면 SQL `NULL`이 아니라 JSON `null`이 저장됐다.** SQLAlchemy `JSONB`는 기본값에서 Python `None`을 `'null'`로 쓴다. 드라이버는 둘 다 `None`으로 돌려줘 테스트가 차이를 잡지 못했다. `WHERE recommendations IS NULL` 분석 쿼리에서 다르게 걸린다.
4. **사유 생성 중 답을 다시 내면 이전 답 기준 사유가 캐시에 남았다.** 요청 A가 LLM을 기다리는 동안(최대 15초) 답 B로 캐시가 비워지고, 뒤늦게 도착한 A 기준 사유가 저장된다. 이후 요청은 세션 만료까지 A 기준 사유를 받는다.

### 사유 내용

5. **템플릿이 소득 자격을 근거 없이 "맞다"고 썼다.** SQL 필터는 소득에서 확실히 안 되는 정책만 지운다. 3,000만~5,000만원 구간 사용자에게 상한 3,500만원 정책이 남는데 "소득(연소득 3,500만원 이하) 자격에 맞는"이라고 썼다. 소득 조건이 '기타'(중위소득 기준 등)인 정책(로컬 DB 442건)도 맞다고 썼다.
6. **'시도 전체'라는 표현이 사실과 달랐다.** 서버의 시도 전체 판정은 "시도 시군구의 80% 이상 포함"(ADR 006)이다. 성남·고양이 빠진 경기도 청년기본소득이 시군구를 답하지 않은 사용자에게 "지역(경기도 전체) 자격에 맞는"으로 나왔다. 프롬프트에도 같은 표현이 사실처럼 들어갔다.
7. **URL 정규식이 한국어 문장에서 오작동했다.** 한글은 정규식에서 단어 문자라 `\b`로 경계를 잡지 못한다. `youthcenter.go.kr에서`는 못 지우고, `온통청년youthcenter.go.kr`은 앞 한글 단어까지 지웠다. 이메일은 `@` 뒤만 지워져 문구가 깨졌다.

### 운영

8. **라우터가 DB 오류를 모두 503 "DB 연결 불가"로 바꾸면서 원인을 남기지 않았다.** `SQLAlchemyError`에는 연결 장애뿐 아니라 SQL 버그(컬럼 없음 등)도 섞이는데, `HTTPException`은 traceback을 남기지 않고 앱에는 전역 예외 로그도 없다.
9. **서버에서 `app.*`의 INFO 로그가 출력되지 않았다(측정 준비 중 발견).** uvicorn 기본 로깅 설정은 `uvicorn` 계열 로거만 잡고 루트 로거는 건드리지 않는다. 루트는 WARNING이라 `app.llm.client`의 토큰 사용량 로그(INFO)가 버려진다. Render도 같은 설정이라 운영 중 LLM 비용을 볼 수 없었다.

처음 구현에서 틀렸던 접근:

- 템플릿 사유의 "맞는 자격"에 SQL 필터를 통과한 조건을 모두 넣었다(5·6번). 필터는 "확실히 안 되는 것만 지운다"는 설계라, 통과했다고 자격이 확정되지 않는다.
- URL을 `\b` 경계 정규식으로 지우려 했다(7번).
- 캐시를 "있으면 반환"으로만 다뤘다(4번). 비우는 쪽만 있고 늦게 도착한 쓰기를 막는 장치가 없었다.

## 배운 점 / 재발 방지

- "실패하면 대체한다"는 설계는 실패가 한 가지 예외로 모일 때만 성립한다. 외부 SDK 경계에서 모든 예외를 감싸고, 시간 한도는 SDK 설정이 아니라 호출 전체에 건다.
- 필터 통과는 자격 확정이 아니다. 사용자에게 "맞다"고 쓰는 문장은 필터가 보장하는 조건만 근거로 삼는다.
- 캐시를 비우는 경로가 있으면, 비운 뒤 늦게 도착한 쓰기를 막는 버전 조건도 함께 둔다.
- 측정에 쓸 로그는 실제 실행 경로(uvicorn 기본 설정)에서 찍히는지 먼저 확인한다. 테스트는 루트 로거의 `caplog`로 받아서 이 문제를 드러내지 못했다.
