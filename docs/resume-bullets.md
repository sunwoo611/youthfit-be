# 이력서·자소서용 기록 (STAR)

작성 규칙: 새 항목은 맨 아래에 추가. 수치가 없으면 `(측정 전)`으로 표시하고 나중에 채운다.
관련 근거 문서(ADR/journal)를 반드시 링크한다.

## 프로젝트 소개 (이력서 상단용)

- **청핏(YouthFit)**: 자연어 한 문장 + 3~5회 선택형 역질문으로 청년 정책 지원금과 우대 적금을 통합 추천하는 LLM 서비스. 백엔드·데이터·AI 담당 (FastAPI, PostgreSQL, OpenAI).

## 항목

### 1. 환각·외부 API 리스크를 고려한 아키텍처 설계

- **Situation**: 공공 API 호출 제한·지연, LLM의 허위 자격 조건/URL 생성 위험이 있는 추천 서비스.
- **Task**: 응답 지연·비용·신뢰성을 동시에 통제하는 구조 설계.
- **Action**: 일 배치로 PostgreSQL에 미러링하고, SQL 1차 필터로 후보를 축소한 뒤 LLM은 역질문/근거 서술에만 사용하도록 설계. 추천 URL·자격 조건은 DB 값만 바인딩. 별도 Vector DB 대신 PostgreSQL 중심(필요 시 pgvector)으로 MVP 범위 통제.
- **Result**: (측정 전) 외부 API 의존 제거, LLM 컨텍스트 축소.
- 근거: [ADR 001](decisions/001-stack-and-mvp-scope.md)

### 2. 문서 간 불일치 정리 및 개발 착수 체계화

- **Situation**: LLM으로 순차 생성한 계획서와 발표자료의 기술 표현(Vector DB)이 불일치.
- **Action**: 두 문서를 대조해 구현 기준을 정하고 ADR로 기록, DB 미연결 상태에서도 기동되는 FastAPI 골격과 테스트를 먼저 구축.
- **Result**: 이후 기술 결정을 ADR/journal로 누적 가능한 구조 마련.
- 근거: [journal 2026-10-12](journal/2026-10-12-project-bootstrap.md)

### 3. 샘플 대신 전수 채움률로 크롤링 여부를 결정

- **Situation**: 프론트 담당이 온통청년 API 정보가 부족하다며 URL 크롤링을 제안했다. 샘플 3건은 신청 URL이 모두 비어 있었다.
- **Task**: 적재본 전체로 필드 채움률을 측정해, 크롤링을 할지 API 데이터로 갈지 숫자로 정한다.
- **Action**: 읽기 전용 리포트로 전체·서울·경기·지역 무관을 나눴다. 서울·경기에서 "URL이 하나도 없음"과 신청·심사·서류의 "별도 문의"/빈 값이 함께 50%를 넘을 때만 참고 URL 선별 보완을 검토하도록 기준을 고정했다.
- **Result**: 정책 3,602건 중 서울·경기 960건. URL이 전혀 없는 비율은 11.9%(신청 URL만 보면 56.8%). 심사 68.8%·서류 69.8%는 빈약하지만 두 조건이 함께 성립하지 않아 크롤링 없이 진행. 8일 전 적재본(정책 3,262건)으로 잰 결과도 같은 결론(13.1%). 적금 홈페이지 매핑 337/337, 청년 상품 8/337. 특정 기간 정책의 신청 종료일 파싱은 1,752/1,753.
- 근거: [journal 2026-10-26](journal/2026-10-26-data-quality-report.md)

### 4. 신청기간이 비어 있는 정책의 신청 가능 여부 판정

- **Situation**: 서울·경기 정책 중 마감을 뺀 추천 후보 583건의 41%(241건)가 신청기간 미지정이라, 이미 끝난 사업이 추천될 위험이 있었다.
- **Task**: 크롤링 없이 원문 데이터만으로 지금 신청할 수 있는 정책을 가려낸다.
- **Action**: 같은 레코드의 사업기간(날짜형·자유 문구)을 정규화했다. 문구는 계속 사업 표현이 하나라도 있으면 마감으로 보지 않는 보수적 규칙을 두고, 실제 문구 26가지를 테스트로 고정했다. 신청 가능 여부는 기준일에 따라 바뀌므로 저장하지 않고 조회 시점에 4상태로 판정했다.
- **Result**: 확인 필요 후보 241건(41%) → 166건(32.9%). 작년에 끝난 사업 78건을 후보에서 제외했고, 문구로 마감 처리한 전국 100건(문구 22종)에서 오판 0건.
- 근거: [ADR 004](decisions/004-policy-availability.md), [journal 2026-10-26](journal/2026-10-26-policy-availability.md)

### 5. 대표 사용자 점검으로 룰 필터 정렬 결함 발견·수정

- **Situation**: 정책 3,602건에서 사용자 조건으로 후보 50건을 고르는 1차 룰 필터를 계획대로 "지역 특화 우선"으로 정렬했다.
- **Task**: LLM 역질문 전에 후보 품질을 실제 사용자 조건으로 검증한다.
- **Action**: 대표 사용자 4명의 상위 후보를 뽑아 상태·지역 범위·링크 출처를 집계했다. 경기 사용자 상위 50건 중 33건이 일부 시군 주민 전용임을 찾고, 시도 시군구 포함 비율(80%)로 "시도 전체 > 전국 > 일부 시군구" 정렬로 바꿨다. 시도 시군구 수는 51ms 걸리던 `unnest` 집계 대신 같은 값을 주는 1.4ms 쿼리로 구했다. 마감 판정은 파이썬 판정 함수와 SQL이 1,024개 날짜 조합에서 같음을 테스트로 고정했다.
- **Result**: 일부 시군 전용 후보 33/50 → 0/50, 응답 중앙값 38~63ms(로컬). 모든 카드에 DB 기반 공식 링크(신청 → 참고 → 공식 상세 페이지)를 붙였다.
- 근거: [ADR 005](decisions/005-official-link-selection.md), [ADR 006](decisions/006-candidate-ranking.md), [journal 2026-10-26](journal/2026-10-26-candidates-filter.md)

### 6. LLM 대신 계산으로 역질문 변수를 고르는 세션 엔진

- **Situation**: 1차 필터 뒤 서울·경기 사용자 후보가 360건을 넘었다. 계획은 LLM이 후보를 보고 역질문을 만드는 방식이었지만, LLM이 고른 변수·선택지가 필터 코드와 어긋나면 엉뚱한 정책이 지워진다.
- **Task**: 역질문 3~5개로 자격이 확실히 없는 정책만 지우고, LLM 없이도 질문 → 답 → 재필터가 끝까지 돌게 한다.
- **Action**: 질문 후보 변수 6개의 코드를 원문과 대조했다. "기타" 코드는 제한으로 보지 않고, "해당자만"과 "우대"가 섞인 특화와 학력 제한과 대부분 겹치는 전공은 빼서 4개(혼인·학력·소득·시군구)로 확정했다. 변수마다 선택지 균등 가정의 기대 제거율로 점수를 매겨 최대 5개를 고르고, 파이썬 판정과 SQL 필터가 같은 결과를 내는지 조합 테스트로 고정했다. 상위 50만 보면 정렬에 밀린 일부 시군 정책(경기 사용자 38건)을 영원히 묻지 않는 문제를 찾아 전체 후보로 점수를 계산했다. 세션은 PostgreSQL에 저장하고 답을 저장된 선택지와 대조했다.
- **Result**: 대표 사용자 4명 모두 질문 3~4개, 전부 답하면 후보 362 → 306, 368 → 295건 등 최대 약 20% 감소. 평택 사용자는 답 뒤 상위 50에 자기 시군 정책 14건이 들어옴(답 전 0건). 세션 생성·답변·조회 로컬 중앙값 31~90ms, 테스트 260건 통과.
- 근거: [ADR 008](decisions/008-question-variable-selection.md), [journal 2026-11-02](journal/2026-11-02-question-engine.md)
